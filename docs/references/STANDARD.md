# 外部项目评判标准

本文件定义什么样的外部项目有资格进入 big-whale。

它不是"好项目"的通用标准，而是**这个项目的适配标准**。一个在别处很优秀的项目，
可能因为不满足我们的数据纪律而完全不能用；一个默默无闻的小仓库，
可能因为解决了我们的一个具体难题而价值极高。

## 一、一票否决项

命中任意一条即淘汰，不进入候选列表，不需要进一步评估。

| 否决项 | 理由 |
|---|---|
| **数据缺失时用估算值静默填充** | 违反第一原则。这类代码会污染整条链路，且污染不可见 |
| **无 LICENSE 文件** | 法律上保留所有权利，不得复制。可以读、可以借鉴思想，但不能 vendoring |
| **GPL / AGPL** | 会传染到整个仓库 |
| **要求把券商凭证交给第三方服务** | 凭证只能存在于我们自己的 Vault |
| **含自动下单能力且与数据层无法剥离** | 当前阶段不开放交易 |
| **宣传收益率、胜率、"稳定盈利"** | 这类项目的回测几乎必然过拟合。宣传口径本身就是质量信号 |

最后一条值得多说一句：一个项目如果在 README 里写"年化 XX%"，
通常意味着作者没有做样本外验证，或者做了但没写不利结果。
**认真的量化项目谈的是 IC、换手、容量和失效条件，不是收益率。**

## 二、评分维度

每项 0–3 分。含 2b 共八项，总分 24。标记 N/A 的项不计入，总分按比例折算。

### 1. 数据真实性纪律（权重最高）

- 3：显式区分实时/延迟/历史；有 staleness 标记；缺数据时明确降级
- 2：有时间戳但无 staleness 语义
- 1：只有数据，无来源元信息
- 0：混用不同时效的数据而不加区分

**这一项低于 2 分的，即使其他维度满分也不采纳代码，只借鉴思路。**

### 2. 执行机制适配性

**这一项只评执行机制，不评信息来源。** 两者是不同的东西，早期版本把它们混在一起，
导致"海外市场数据"被误判为不相关。见下一项。

一个项目如果要参与我们的成交假设、回测或下单前判断，它必须理解 A 股的交易规则：

- T+1 限制
- 涨跌停（且理解"触及涨停 = 买不进"而非"按涨停价成交"）
- 停牌与复牌
- ST / 退市整理
- 除权除息复权口径

- 3：全部处理且口径明确
- 2：处理主要项
- 1：仅处理涨跌停
- 0：直接套用他国市场的成交假设

**不适用的情况**：纯数据源、纯信息类项目不参与成交假设，本项记「N/A」，不计入总分，
总分按比例折算。一个提供美股行情的库不需要懂 T+1。

### 2b. 跨市场信息价值

海外市场数据对 A 股**有实质参考价值**，这一项独立加分：

- **走向指引**：美股隔夜、日韩早盘对 A 股开盘情绪有传导，尤其在事件驱动时段
- **产业链关联**：日韩半导体、美股龙头的业绩与指引，直接关系到 A 股对应产业链标的
- **全球宏观**：美债利率、美元指数、大宗商品对 A 股的影响，往往先反映在这些市场上
- **共同因子**：全球风险偏好、行业景气度是跨市场共享的，可用于分离"个股因素"与"系统因素"

因此提供美股 / 日股 / 韩股 / 港股数据的项目，**不因"不是 A 股"而降分**。

- 3：多市场覆盖且时区、交易日历、货币口径处理正确
- 2：覆盖但需要我们自己处理时区与日历对齐
- 1：单一海外市场，数据可用
- 0：不涉及

**时区与交易日历对齐是这里最容易出错的地方**，也是评分的主要区分点：
美股收盘对应 A 股的哪个交易日、隔夜数据算 T-1 还是 T，弄错就会引入前视偏差。

### 3. 可验证性

- 3：核心逻辑是纯函数且有测试
- 2：有测试但覆盖表层
- 1：无测试但逻辑可读、易于我们自己补测
- 0：逻辑与 I/O 深度纠缠，无法单独测试

### 4. 维护活跃度

- 3：近三个月有实质提交，issue 有响应
- 2：近一年有维护
- 1：停更但代码完整可读
- 0：停更且有未修复的已知严重问题

停更**不是**否决项。一个写得好的死项目，其设计依然可以借鉴。

### 5. 依赖负担

- 3：标准库为主，或依赖少且都是主流
- 2：依赖较多但都可替换
- 1：绑定特定框架
- 0：绑定特定商业服务或闭源 SDK

### 6. 可拆解性

能否只取一个模块而不拖进整个体系。

- 3：模块边界清晰，可单独提取
- 2：需要少量适配
- 1：耦合较深，等于重写
- 0：不可拆

### 7. 与我们缺口的相关度

- 3：直接解决一个已知缺口（见下）
- 2：解决一个次要问题
- 1：有参考价值但不紧急
- 0：我们已经有更好的方案

## 三、当前已知缺口（相关度 3 分的判据）

按优先级排序。这个列表会随项目推进更新。

1. **回测框架** —— Rank IC / ICIR / 分层单调性 / 样本外划分，且正确处理 A 股成交约束
2. **QMT / XtQuant 能力探测** —— installed → SDK → broker → entitlement → fresh 的分层判定
3. **Level-2 逐笔数据的规范化** —— 逐笔成交、逐笔委托、撤单的统一表示
4. **期权链数据的 provenance** —— 特别是能提供真实交易所时间戳的源
5. **资金流真实口径** —— 区分主动买卖、大单分级的可靠算法
6. **交易日历与停复牌** —— 权威、可离线、含盘中临时停牌
7. **财务数据 point-in-time** —— 避免财报回填造成的前视偏差
8. **跨市场数据与对齐** —— 美 / 日 / 韩 / 港行情与交易日历，且时区与 T 日归属口径明确

## 四、准入流程

```
发现 → 一票否决筛查 → 评分 → 写入 CANDIDATES.md → 用户确认 → ADR → 实现 → 记录
```

- **折算后达 70% 且第 1 项 ≥ 2**：进入候选列表，标记「建议采纳」
- **折算后 45%–70%**：进入候选列表，标记「值得借鉴思路」
- **折算后 < 45%**：不入列表，但如果有单点亮点，记在 `docs/references/` 的对应文件里

**评分不是决定，是把判断依据摆出来。** 最终是否采纳由用户确认。

## 五、评估纪律

**读代码，不读 README。** README 描述的是作者的意图，代码是实际做的事。
两者不一致的地方往往正是最需要知道的地方。

**不确定就写不确定。** 没读到的部分标 `pending verification`，不靠推测补全。

**记录否决理由。** 否决项和采纳项同样重要——它防止后人重走已经走过的弯路。

**承认自己的偏好。** 评分者会系统性偏好和自己风格相近的代码。
遇到风格陌生但设计合理的项目时，要额外警惕这种偏差。
