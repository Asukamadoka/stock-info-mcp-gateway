# v0.1.1 Source Hardening Design

## Goal

Turn the v0.1 reverse-synced production snapshot into a maintainable,
typed, GitHub-first source baseline without changing production behavior
until verification is complete.

## Safety Boundary

Only the isolated Supabase project is in scope:

- project: stock-info-mcp-gateway
- project ref: aneonwkxfhgqywtczmvc

No unrelated Supabase project may be read from or modified by this workflow.

Production deployment remains disabled until the v0.1.1 PR is reviewed,
CI is green, and read-only smoke tests are defined.

## 1. Canonical Source Recovery

Use the Supabase Management API from the authenticated Codespaces environment
to retrieve Edge Function source bodies.

Functions:

- mcp
- mcp-v3
- mcp-options
- mcp-htsc

First probe only `mcp`.

Success criteria:

- response is retrieved successfully
- returned source contains original TypeScript annotations, e.g.
  `url:string`, `req:Request`, or equivalent typed source
- returned source is not merely the ESZip runtime snapshot currently stored
  in GitHub

Only after the probe succeeds may the remaining three functions be recovered.

The canonical files will replace the v0.1 runtime snapshots and remove
`@ts-nocheck`.

## 2. Type Safety

Once canonical typed source is restored:

- `deno.json` remains strict
- CI changes from snapshot/module validation to true strict TypeScript checks
- all four functions must pass `deno check`
- no `@ts-nocheck` remains in canonical Edge Function source

## 3. HTSC Secret Cache

Current production `mcp-htsc` caches Vault secrets indefinitely in a warm
Edge Function instance.

Replace permanent caching with a 60-second TTL cache:

- cache entry contains value and timestamp
- cached value is reused only while age < 60 seconds
- after TTL expiry, value is re-read from Supabase Vault

This applies to the HTSC API key and gateway authentication secret.

No secret values may be logged, committed, returned, or exposed.

## 4. Gateway Authentication Separation

The gateway must stop using the Jin10 upstream credential as its long-term
client authentication credential.

Migration design:

1. introduce Vault secret `gateway_bearer_token`
2. authenticate clients against `gateway_bearer_token`
3. temporarily accept `jin10_bearer_token` as a compatibility fallback
4. migrate clients
5. remove the fallback in a later release

v0.1.1 must not break existing clients during this transition.

No token values belong in GitHub.

## 5. source_status Accuracy

Remove obsolete deployment strings such as:

- `mcp v2 remains untouched`
- `staging_function: mcp-v3`
- GitHub sync blocked status that is no longer accurate

Replace them with state-oriented fields that do not hard-code historical
deployment assumptions.

Suggested structure:

- gateway version
- production router
- active components
- source families
- auth mode
- GitHub source-of-truth state

## 6. HTSC Read-only Verification

After code review and production deployment, verify only read operations:

1. gateway GET health
2. MCP initialize
3. tools/list
4. ht_get_quote
5. ht_query_indicator
6. ht_select_stock
7. ht_market_insight
8. ht_get_account_balance

Do not execute:

- simulated orders
- cancellations
- addWatchlist
- other mutating HTSC tools

A successful deployment does not prove the new HTSC API key works.
Business-level success responses are required.

## 7. Deployment Sequence

The required order is:

GitHub feature branch
→ canonical source recovery
→ tests / strict Deno check
→ PR
→ review
→ merge to main
→ GitHub/Supabase production deployment
→ read-only smoke tests
→ production verification

Production must never be used as the first test environment for new behavior.

## 8. Out of Scope

v0.1.1 does not include:

- Put Pressure
- option snapshot persistence
- PCR
- Delta OI
- Put Wall
- Python worker
- broader a-stock-data endpoint promotion
- real-money broker trading

Those remain later milestones.
